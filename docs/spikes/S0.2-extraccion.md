# Spike S0.2 — Elección del extractor de PDF

**Pregunta:** ¿qué librería extrae mejor la estructura y el texto de PDFs variados para la
pipeline PDF→audio?

**Estado: ✅ decidido — `pymupdf4llm` como extractor por defecto del MVP.**

## Corpus de prueba (en `spikes/s02-extraction/pdfs/`)

Sin acceso a los PDFs personales del autor en esta sesión, se usó un corpus público variado
(test suites de pdf.js, pdfplumber, py-pdf y tabula):

| PDF | Tipo | Por qué está |
|---|---|---|
| paper-2col.pdf | Paper académico ACM a 2 columnas, 14 págs | El caso nº 1 del autor: orden de lectura multicolumna |
| libro-latex.pdf | Libro LaTeX (alemán), capítulos + índice, ~130 págs | Documentos largos con jerarquía profunda |
| tablas-complejas.pdf | Tabla con celdas fusionadas | Peor caso de tablas |
| transcript.pdf | Transcripción judicial con números de línea | Layout hostil no estándar |
| escaneado.pdf | Formulario/informe (con capa de texto) | Documento administrativo real |

## Resultados

### pymupdf4llm (ejecutado aquí, CPU, sin modelos)

| PDF | Tiempo | Salida | Calidad observada |
|---|---|---|---|
| paper-2col | 4,8 s | 85k chars, 28 headings | **Excelente**: orden de lectura 2-col correcto, jerarquía de secciones numeradas bien detectada (`## 1. Introduction`, `### 3.1 Traces`) |
| libro-latex | 18,4 s | 170k chars, 336 headings | **Buena**: capítulos e índice detectados; ruido menor (números de página sueltos como `#### 9`) |
| tablas-complejas | 0,3 s | tabla Markdown | **Usable**: celdas extraídas; las celdas fusionadas del encabezado se trocean (`I|mproved op|eration...`) |
| transcript | 0,2 s | 779 chars | **Pobre**: números de línea pegados al texto — layout hostil, esperable |
| escaneado | 1,1 s | 7,6k chars, 12 headings | **Buena** (tenía capa de texto; un escaneado puro sin OCR daría vacío — confirma RF-1.7 como C) |

### docling — bloqueado en este entorno

Instala pero al convertir necesita descargar sus modelos de layout desde huggingface.co,
que la política de red de esta sesión bloquea (`ProxyError: 403`). No evaluable aquí.

### marker — descartado del spike

Misma dependencia de modelos HF + orientado a GPU; incompatible con la restricción de red
y con el objetivo de self-host ligero del MVP.

## Decisión

**`pymupdf4llm` es el extractor por defecto del MVP**, por cuatro razones:

1. **Calidad suficiente en el caso principal** (papers multicolumna: orden y jerarquía correctos).
2. **Cero modelos que descargar**: arranca en cualquier VPS/self-host sin GPU ni tráfico a HF — ventaja real para el proyecto OSS (RNF-6).
3. **Velocidad**: 0,2-18 s por documento en CPU — irrelevante frente a los minutos del TTS.
4. Sus defectos (celdas fusionadas, layouts hostiles, ruido de números de página) **los absorbe la etapa de limpieza con LLM (RF-1.4)** que la pipeline tiene de todas formas: el extractor no necesita ser perfecto, necesita no perder contenido ni romper el orden.

**docling queda como segundo extractor** detrás de la interfaz `Extractor` (A12), a evaluar
en el VPS del autor (sin bloqueo de red) cuando lleguen tablas/figuras habladas (RF-1.5, v1):
sus modelos de layout prometen mejores tablas y detección de figuras.

## Reproducir

```bash
python -m venv venv && venv/bin/pip install pymupdf4llm docling
venv/bin/python spikes/s02-extraction/run_compare.py            # ambos
venv/bin/python spikes/s02-extraction/run_compare.py pymupdf4llm # solo uno
# salidas en spikes/s02-extraction/out/
```
